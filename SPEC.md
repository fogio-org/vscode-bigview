# ТЗ: BigView — просмотр и поиск в очень больших файлах внутри VS Code

## 0. Как работать с этим документом

Ты реализуешь проект с нуля до работающего расширения. Документ разбит на майлстоуны. **Идти строго по порядку, каждый майлстоун заканчивать рабочей сборкой и прогнанными тестами.** Не забегать вперёд, не реализовывать фичи из будущих майлстоунов «заодно».

Если техническое решение в разделе «Зафиксированные решения» противоречит твоему предпочтению — следуй документу. Эти решения приняты после анализа конкурентов, у которых сломалось именно то, что здесь зафиксировано.

Перед началом работы прочитай весь документ целиком.

## 1. Задача

VS Code отказывается открывать большие файлы, а на 50–200 МБ начинает подвисать и падать. Существующие расширения решают половину проблемы: они умеют **показать** большой файл, но не умеют **искать по нему целиком**. Поиск ограничен видимой областью, сортировка — загруженной страницей, фильтр — тем, что уже в памяти.

BigView закрывает именно эту дыру: открыть файл любого размера, мгновенно прокручивать, и выполнить поиск/фильтрацию **по всему файлу**, не загружая его в память.

### Целевые сценарии

1. Открыть лог на 3 ГБ, найти все строки с конкретным `trace_id`, посмотреть окрестности каждого попадания.
2. Открыть JSONL на 800 МБ, отфильтровать по `level=error`, выгрузить результат в отдельный файл.
3. Открыть CSV на 2 ГБ, перейти к строке 14 000 000, посмотреть её в табличном виде.
4. Смотреть растущий лог в реальном времени (tail) с активным фильтром.

### Метрики успеха (это acceptance-критерии, не пожелания)

| Операция | Файл 1 ГБ | Файл 5 ГБ |
|---|---|---|
| Первая отрисовка (до готовности индекса) | < 300 мс | < 300 мс |
| Построение индекса (фоном) | < 12 с | < 60 с |
| Прокрутка | 60 fps, без рывков | 60 fps |
| Литеральный поиск по всему файлу | < 6 с | < 30 с |
| Пиковое потребление RAM процессом расширения | < 250 МБ | < 400 МБ |
| Переход к произвольной строке (индекс готов) | < 50 мс | < 50 мс |

Потребление памяти — самый важный критерий. Если он нарушен, реализация неверна независимо от скорости.

## 2. Чего НЕ делаем

Это рамки. Не выходить за них без явной команды.

- **Никакого редактирования.** Вьюер строго read-only. Редактирование гигабайтных файлов — другой продукт.
- **Никакого AI**, никаких вызовов LLM, никаких сетевых запросов вообще. Расширение полностью офлайновое.
- **Не делаем подсветку синтаксиса** через TextMate/Shiki в MVP. Только раскраска уровней логов простым regex.
- **Не поддерживаем удалённые файлы** (http://, s3://) в MVP.
- **Не делаем свой формат запросов/DSL** в MVP. Фильтры — это regex плюс несколько предустановленных предикатов.
- **Не трогаем parquet** в MVP.
- **Не делаем телеметрию.** Вообще. Ни одного исходящего байта.

## 3. Зафиксированные решения

Эти решения не обсуждаются, каждое принято по конкретной причине.

### 3.1 Файловый доступ — только `node:fs`, не `vscode.workspace.fs`

`vscode.workspace.fs` не даёт random access, только чтение файла целиком. Использовать `fs.promises.open()` и `FileHandle.read(buffer, offset, length, position)`.

### 3.2 Вся тяжёлая работа — в `worker_threads`

Extension host однопоточный и общий на все расширения. Блокировка его на 10 секунд индексации — это подвисший на 10 секунд редактор пользователя. Индексация, поиск и фильтрация живут в воркерах. В extension host остаётся только оркестрация и мелкие чтения для отрисовки вьюпорта.

### 3.3 Индекс — это массив байтовых смещений начала строк

Ядро продукта. Один последовательный проход по файлу, поиск байта `0x0A`, запись смещения следующего байта.

Хранение: `Float64Array`. Не `Uint32Array` (ломается на файлах > 4 ГБ) и не `BigInt64Array` (медленнее и тяжелее в сериализации). Float64 точно представляет целые до 2^53, этого хватит на любой реальный файл.

Память индекса: 8 байт на строку. Лог на 5 ГБ со средней строкой 200 байт — это 25 млн строк = 200 МБ. **Это слишком много.** Поэтому:

> **Разреженный индекс.** Хранить каждое N-е смещение, где N подбирается так, чтобы индекс не превышал 32 МБ. Между опорными точками строки досчитываются на лету при чтении нужного чанка. N вычисляется как `max(1, ceil(estimatedLines / 4_000_000))`. Оценка числа строк делается по первым 4 МБ файла.

### 3.4 Индекс кешируется на диск (sidecar)

Путь: `context.globalStorageUri/index/<sha256(absPath)>.idx`.

Формат (little-endian):
```
magic      u32   0x42475631  ("BGV1")
version    u32   1
fileSize   f64
mtimeMs    f64
stride     u32   разреженность N
count      u32   число сохранённых смещений
offsets    f64[count]
```

Инвалидация: если `fileSize` или `mtimeMs` не совпали — индекс пересобирается. Никаких хешей содержимого, это слишком дорого.

Уборка: при активации удалять индексы, к которым не обращались более 30 дней, и держать общий размер кеша под 500 МБ (LRU).

### 3.5 UI — `CustomReadonlyEditorProvider` + webview

Регистрируем провайдер для расширений `.log`, `.jsonl`, `.ndjson`, `.csv`, `.tsv` и команду `BigView: Open File in BigView` для любого файла.

Внутри webview — **собственная виртуализация**. Никакого Monaco внутри webview, никаких сторонних грид-библиотек. Рендерим только видимые строки плюс буфер в 50 строк сверху и снизу. Абсолютно позиционированный контейнер с высотой `lineCount * lineHeight` создаёт скроллбар, содержимое перерисовывается на событии scroll с `requestAnimationFrame`-троттлингом.

### 3.6 Протокол webview ↔ extension host

Обмен по `postMessage`, но **никогда не передавать большие объёмы за раз**. Максимум 500 строк в одном сообщении. Результаты поиска стримятся батчами по 200 попаданий с интервалом не чаще чем раз в 100 мс.

Все сообщения типизированы, схема в `src/shared/protocol.ts`, используется обеими сторонами.

### 3.7 Обработка кодировок и переводов строк

- Читаем байты, декодируем в UTF-8 **только видимые строки**, в extension host, через `TextDecoder`.
- Чанки при индексации и поиске читаются с перекрытием в 4 КБ, чтобы не разрезать многобайтовый символ и не потерять строку на границе.
- `\r\n` обрабатывается: индекс хранит смещения после `\n`, при декодировании отрезается хвостовой `\r`.
- Если в первых 4 МБ встречается байт `0x00` — считаем файл бинарным, показываем предупреждение и предлагаем hex-режим (в MVP — просто предупреждение и отказ).

### 3.8 Поиск

Отдельный воркер. Читает файл чанками по 8 МБ с перекрытием. Для литерального поиска — `Buffer.indexOf` по сырым байтам (значительно быстрее, чем декодировать всё в строки). Для regex — декодируем чанк и гоняем regex построчно.

Поиск **отменяемый**: новый запрос убивает предыдущий. Воркер проверяет флаг отмены между чанками.

Прогресс репортится каждые 64 МБ обработанных байт.

### 3.9 Лицензирование

В MVP **всё бесплатно и открыто**. Но заложить модуль `src/license.ts` с единственной функцией `isPro(): boolean`, которая пока всегда возвращает `true`, и вызывать её в местах будущего гейта (размер файла > 200 МБ, экспорт, tail, сохранённые фильтры). Это чтобы потом не переписывать.

## 4. Стек

- TypeScript, strict mode, `noUncheckedIndexedAccess: true`
- Сборка: `esbuild` (extension host, worker, webview — три отдельных бандла)
- Тесты: `vitest` для юнитов, `@vscode/test-electron` для интеграционных
- Линт: `eslint` + `@typescript-eslint`
- Минимальная версия VS Code: `^1.90.0`
- Node API: только то, что доступно в extension host (Node 20+)
- **Ноль рантайм-зависимостей.** Никаких библиотек в `dependencies`. Всё нужное пишем сами. Это принципиально: расширение должно устанавливаться мгновенно и не иметь цепочки supply-chain рисков.

## 6. Майлстоуны

### M1 — Скелет и чтение (цель: открыть файл 1 ГБ и проскроллить его)

1. Инициализировать проект, esbuild, три бандла, F5-запуск в Extension Development Host.
2. `test/fixtures/generate.ts`: генератор файлов. Параметры: размер, формат (log/jsonl/csv), средняя длина строки, доля строк с заданным маркером. Файлы **не коммитим**, генерируем перед тестами в `test/.tmp/`.
3. `FileHandlePool`, `ChunkReader`, `LineIndex` (пока плотный индекс, в памяти, без разреженности и без диска).
4. `indexer.worker.ts` — построение индекса в воркере с репортом прогресса.
5. `BigViewProvider` + минимальный webview: виртуальный список, монохромный текст, номера строк, скролл.
6. Команда `BigView: Open File in BigView`.

**Acceptance M1:** файл 1 ГБ открывается, показывает первую страницу быстрее чем за 500 мс (с индикатором «индексируется»), после индексации скроллится плавно от начала до конца, включая прыжок скроллбаром в середину.

---

### M2 — Разреженный индекс и кеш на диске (цель: удержать память)

1. Переделать `LineIndex` на разреженный, с досчётом строк между опорными точками.
2. `IndexStore`: бинарный формат, запись, чтение, валидация по size+mtime, LRU-уборка.
3. Показывать в статус-баре: размер файла, число строк, состояние индекса.
4. Команда перехода к строке (`Ctrl+G`).

**Acceptance M2:** файл 5 ГБ индексируется один раз, при повторном открытии индекс подхватывается с диска мгновенно. Пиковая память процесса расширения не превышает 400 МБ (мерить через `process.memoryUsage().rss`, зафиксировать замер в тесте).

---

### M3 — Поиск по всему файлу (цель: главная фича)

1. `search.worker.ts`: литеральный поиск через `Buffer.indexOf`, regex-поиск построчно.
2. Отмена предыдущего поиска при новом запросе.
3. Стриминг результатов батчами, прогресс-бар.
4. UI: панель поиска, счётчик попаданий, список результатов, `F3`/`Shift+F3` для перехода, подсветка попаданий в основном списке.
5. Переключатели: регистр, целое слово, regex.

**Acceptance M3:** в сгенерированном файле 1 ГБ, где ровно 137 строк содержат маркер `NEEDLE_MARKER`, поиск находит ровно 137 попаданий быстрее чем за 6 секунд, и клик по любому результату переводит основной список на нужную строку. Есть тест, который это проверяет.

---

### M4 — Фильтр-режим (цель: показывать только совпавшие строки)

1. Режим «только совпадения»: список показывает не весь файл, а подмножество строк.
2. Результат фильтра — отдельный массив номеров строк, виртуализация работает по нему.
3. Фильтр применяется поверх поиска, можно инвертировать (исключающий фильтр).
4. Экспорт текущей выборки в новый файл (`BigView: Export Filtered Lines`), потоковая запись.

**Acceptance M4:** фильтр по regex на файле 1 ГБ строится за то же время, что и поиск, переключение между полным и отфильтрованным видом мгновенное, экспорт 500 000 строк не поднимает память.

---

### M5 — Форматы (цель: смысловое отображение)

1. `logFormat`: детект уровня по regex, раскраска строки по уровню, детект и парсинг таймстемпа в начале строки, предикат фильтра по диапазону времени.
2. `jsonlFormat`: разбор строки как JSON, боковая панель с pretty-view выбранной строки, фильтр по полю (`field=value`, `field~regex`).
3. `dsvFormat`: определение разделителя, заголовок из первой строки, табличный рендер с виртуализацией по строкам, ресайз колонок. Сортировка — **не делаем** (честно пишем в README, что сортировка всего файла требует внешней сортировки и это отдельная задача).

**Acceptance M5:** каждый формат открывается в своём представлении, переключение формата вручную доступно через команду.

---

### M6 — Tail и полировка

1. `TailWatcher`: `fs.watch` на файл, при росте — дочитывание с последнего смещения, дописывание в индекс, автоскролл вниз если пользователь в конце.
2. Обработка ротации лога (файл усох или сменился inode) — переиндексация.
3. Сообщения об ошибках: нет прав, файл удалён, бинарный файл, диск заполнен при записи индекса.
4. README со скриншотами, `CHANGELOG.md`, иконка, `package.json` с категориями и keywords.
5. `.vscodeignore`, чтобы в VSIX не попали исходники и фикстуры.

**Acceptance M6:** tail работает на растущем файле, ротация не ломает вьюер, VSIX собирается и весит меньше 500 КБ.

## 7. Известные ловушки

Это места, где конкуренты сломались. Отнестись серьёзно.

1. **Никогда не вызывать `fs.readFile` на целевом файле.** Ни разу, ни в одном месте. Если видишь такой вызов — это баг.
2. **Не декодировать в строку больше, чем нужно для отрисовки.** Соблазн «декодирую чанк целиком, потом порежу» убивает память.
3. **Границы чанков.** Строка может пересекать границу. Многобайтовый символ UTF-8 может пересекать границу. Тесты обязаны включать файл, где маркер лежит ровно на границе 8 МБ, и файл с кириллицей/эмодзи на границе.
4. **`postMessage` в webview — не бесплатный.** Пересылка 100 000 строк одним сообщением подвесит и host, и webview. Батчить всегда.
5. **Не держать открытым дескриптор навсегда.** `FileHandlePool` с LRU и закрытием по таймауту, иначе на Windows файл нельзя будет удалить.
6. **Скроллбар браузера ломается на больших высотах.** Контейнер высотой `25_000_000 * 20px` = 500 млн пикселей. Chromium обрезает высоту примерно на 33 млн пикселей. Решение: **виртуальный скроллбар** — контейнер фиксированной разумной высоты (например, 1 млн px), а маппинг позиции скролла в номер строки делается вручную с коэффициентом. Это обязательно, иначе на файлах свыше ~1,6 млн строк прыжки скроллом станут неточными.
7. **Воркер не должен сериализовать индекс через structured clone на каждый запрос.** Передавать `Float64Array` через `transferList` один раз, либо держать индекс в `SharedArrayBuffer`.
8. **Отмена поиска должна реально останавливать воркер.** Проверка флага между чанками, а не `worker.terminate()` на каждый ввод символа (терминация и рестарт воркера дороже, чем сам поиск на малых файлах). Дебаунс ввода 250 мс.

## 8. Тестирование

### Юниты (`vitest`)
- `LineIndex`: маппинг строка↔смещение при разных `stride`, краевые случаи (первая строка, последняя, файл без завершающего `\n`, пустой файл, файл из одной строки без `\n`).
- Границы чанков: маркер на границе, UTF-8 символ на границе, `\r\n` на границе.
- `IndexStore`: запись/чтение round-trip, инвалидация при изменении mtime и размера, порченый magic, обрезанный файл индекса.
- Формат-детекторы.

### Интеграционные (`@vscode/test-electron`)
- Открытие сгенерированных файлов 10 МБ / 200 МБ / 1 ГБ.
- Поиск с известным числом попаданий.
- Фильтр и экспорт с проверкой содержимого результата.
- Замер пиковой RSS, падение теста при превышении порога.

### Перф-тесты
Отдельный скрипт `npm run bench`, печатает таблицу из раздела 1 и сравнивает с порогами. Запускать перед каждым релизом.

## 9. Первый шаг

Начни с `test/fixtures/generate.ts` и юнит-тестов на `LineIndex`. Всё остальное строится вокруг корректности индекса — если он врёт, врёт весь продукт. Сначала сделай так, чтобы индекс был доказуемо правильным на краевых случаях, и только потом занимайся UI.
